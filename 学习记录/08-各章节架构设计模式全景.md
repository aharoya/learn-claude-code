## 二、分章详解

### s01 — Agent Loop（最核心，永不变）

```python
def agent_loop(messages):
    while True:
        response = client.messages.create(model=MODEL, system=SYSTEM, messages=messages, tools=TOOLS)
        messages.append({"role": "assistant", "content": response.content})
        if response.stop_reason != "tool_use":
            return
        results = [{"type": "tool_result", "tool_use_id": block.id,
                    "content": TOOL_HANDLERS[block.name](**block.input)}
                   for block in response.content if block.type == "tool_use"]
        messages.append({"role": "user", "content": results})
```

**模式：Agent Loop（决策-行动循环）**。这是整个 Harness 的地基。所有后续章节都是在这 20 行之外"外挂"机制，循环本身从不修改。

本质结构：`观察（读消息）→ 决策（LLM 生成）→ 行动（工具执行）→ 观察（写回结果）→ 循环`。

与解释器循环（REPL：Read-Eval-Print-Loop）同构——LLM 就是那个"Eval"，工具调用就是"副作用"。

---

### s02 — 工具分发

```python
TOOL_HANDLERS = {"bash": run_bash, "read_file": run_read, ...}
# 模型选中工具名 → 查表 → 执行
output = TOOL_HANDLERS[block.name](**block.input)
```

**模式：策略模式 + 注册表（Registry）**。

- **策略模式**：每个工具是一个"策略"，模型根据任务选择调用哪个策略，运行时通过 `block.name` 动态选择执行路径，不用 if/else 硬编码。
- **注册表**：`TOOL_HANDLERS` 字典是"名称 → 实现"的注册表。新增工具 = 注册一条映射，不改循环。

关键设计：**模型的输出（工具名 + 参数）就是"策略选择"的结果**。模型是决策者，代码是执行者——这就是 Agent 自主性的来源。

---

### s03 — 权限门

```python
def check_permission(block) -> bool:
    if check_deny_list(...): return False   # 闸门 1：硬拒绝
    reason = check_rules(...)               # 闸门 2：规则匹配
    if reason and ask_user(...) == "deny":  # 闸门 3：用户审批
        return False
    return True
```

**模式：责任链（Chain of Responsibility）**。三道闸门串成一条过滤管线，每道闸门只负责一种决策：

| 闸门 | 职责 | 命中后 |
|------|------|--------|
| 1 硬拒绝 | 永远禁止的操作 | 直接拒绝 |
| 2 规则匹配 | 看上下文的操作 | 交给闸门 3 |
| 3 用户审批 | 人类决定 | 允许或拒绝 |

**核心思想：安全不靠信任模型，靠代码在工具执行前拦截**。这是"信任边界"（Trust Boundary）的概念——把执行路径分成可信/需审批两层。

### s04 — Hooks

```python
HOOKS = {"UserPromptSubmit": [], "PreToolUse": [], "PostToolUse": [], "Stop": []}

def register_hook(event, callback): HOOKS[event].append(callback)
def trigger_hooks(event, *args):
    for cb in HOOKS[event]:
        result = cb(*args)
        if result is not None: return result   # 非 None = 拦截
    return None
```

**模式：观察者模式（Observer）/ 事件发布-订阅（Pub-Sub）**。

- 循环是"主题"（Subject），只发布事件（`trigger_hooks`）
- 扩展逻辑是"观察者"（Observer），通过 `register_hook` 订阅
- **循环不再直接调用任何检查函数**，扩展点全部外挂

**关键转折**：s03 是把 `check_permission()` 硬编码在循环里；s04 把检查从循环体移到了 hook 上。循环从此稳定，扩展靠注册表。

---

### s05 — TodoWrite

```python
CURRENT_TODOS = []
def run_todo_write(todos): CURRENT_TODOS = todos   # 全量替换
```

**模式：规划-执行分离（Plan-Execute Separation）**。

- todo_write 工具**不增加任何执行能力**，只增加规划能力
- Agent 先列步骤（全 pending）→ 执行 → 更新状态 → 下一步

核心洞察：给 Agent 一个"工作记忆"（working memory）存放计划，防止长任务中计划被上下文挤出注意力。教学版用内存全局变量，s12 的 Task 系统升级为文件持久化。

---

### s06 — 子 Agent

```python
def spawn_subagent(description) -> str:
    messages = [{"role": "user", "content": description}]  # 全新上下文
    for _ in range(30):  # 独立循环
        ...
    return extract_text(messages[-1]["content"])            # 只回传结论
```

**模式：函数调用范式（Function Call Paradigm）**。

- 子 Agent 是"一个函数"：输入描述，阻塞执行，返回结论
- 上下文隔离 = "函数栈隔离"：子 Agent 的中间过程不污染父 Agent
- 只回传结论 = "返回值"：中间结果全部丢弃

这是**过程式思维**的协作方式（与 s15 的 Actor 消息传递形成对比）。适用于"临时工"——叫来干一件事，拿结论就走。

---

### s07 — 技能加载

```python
# Layer 1：启动时注入目录（元数据）
SYSTEM = f"Skills available:\n{catalog}"     # ~100 tokens/技能
# Layer 2：运行时 load_skill（内容）
def load_skill(name): return SKILL_REGISTRY[name]["content"]  # ~2000 tokens/技能
```

**模式：懒加载（Lazy Loading）+ 两级缓存**。

- **第一级**：启动时只注入"目录"（有哪些技能、描述）——便宜
- **第二级**：Agent 需要时才 `load_skill` 加载完整内容——昂贵

**核心思想：不该提前带的不要带，用到才花 token**。这与 s08 的 compact 天然衔接——懒加载解决"不该提前带的不要带"，compact 解决"该丢的怎么丢"。

### s08 — 上下文压缩

```python
def compress_messages(messages):
    # L1: 裁剪（最便宜）
    # L2: 摘要 tool_result
    # L3: 摘要 assistant 消息
    # L4: 递归深度压缩（最贵）
```

**模式：分级降级策略（Hierarchical Degradation）+ 策略模式**。

- 压缩策略按代价从便宜到贵排序（L1-L4）
- 每种压缩是独立"策略"，可组合、可触发
- 自动触发机制监控上下文大小，达到阈值逐级启用

**核心思想：成本分层，便宜的先用，贵的兜底**。这是资源受限系统的通用策略——与数据库查询优化、缓存淘汰（LRU）同思路。

### s09 — 持久化记忆

```python
def pre_compress(messages):         # ① 压缩前快照
    return extract_key_info(messages)
def extract_memory(query):          # ② 侧查询
    return client.messages.create(...)  # 另开 LLM 调用提取
def save_memory():                  # ③ 删除旧记忆 + 写入新记忆
```

**模式：快照 + 侧查询（Snapshot + Side-Query）**。

- **快照**：压缩前先把关键信息复制出来，防止压缩丢信息
- **侧查询**：提取记忆时另开一次 LLM 调用（不是复用对话），只关心提取这一个目标
- **删除后写入**：先清旧记忆再写新记忆，避免新旧叠加冲突

**核心思想：记忆系统的核心不是"存"，而是"在什么时机提取"**。压缩触发 → 提取 → 固化 → 跨会话恢复，是一条流水线。

### s10 — 系统提示词

```python
PROMPT_SECTIONS = {"identity": ..., "tools": ..., "workspace": ..., "memory": ...}
def assemble_system_prompt(context): ...   # 按需拼接
def get_system_prompt(context):            # 确定性缓存
```

**模式：模板方法 + 缓存（Template Method + Cache）**。

- 系统提示词不是静态字符串，而是运行时按 `context` 动态组装
- 片段字典（PROMPT_SECTIONS）是"模板"，`context` 是变量
- 确定性缓存：context 没变就不重算，省 token

**与 s07 对比**：s07 的 SYSTEM 启动时构建一次就固定；s10 的 SYSTEM 每轮根据运行时状态刷新。

### s11 — 错误恢复

```python
def call_llm_with_retry(...):
    for attempt in range(3):
        try: return client.messages.create(...)
        except Exception: time.sleep(2 ** attempt)   # 指数退避
    # 降级：换成更便宜的模型 / 截断消息
```

**模式：重试 + 降级（Retry with Backoff + Degradation）**。这是**模板方法**——错误恢复的骨架固定（检测→重试→降级→预算保护），每步的具体策略可替换。

**核心思想：LLM 调用不可靠，Harness 必须自己兜底**。分级重试、降级模型、token 预算保护，都是为了让 Agent 在 API 故障时仍能完成工作。

### s12 — 任务系统

```python
@dataclass
class Task: id, subject, description, status, owner, blockedBy

def create_task(...)   # CRUD
def claim_task(...)    # 认领（依赖检查）
def complete_task(...) # 完成（级联解锁）
```

**模式：领域模型 + 仓储模式（Domain Model + Repository）**。

- **领域模型**：Task 是核心实体，status/owner/blockedBy 是领域概念，不是随意字段
- **仓储**：所有 CRUD 通过 `_task_path` 落盘到 `.tasks/*.json`——文件即数据库
- **依赖图**：blockedBy 构成 DAG，`can_start` 检查依赖是否满足

**与 s05 Todo 对比**：Todo 是内存便签（退出即丢），Task 是持久化工单（跨会话 + 依赖 + owner）。

**关键设计**：任务操作是 **Tool 不是 Subagent**——Task 是数据层（描述"有什么活"），Subagent 是执行层（描述"谁去干"）。数据与执行分离。

### s13 — 后台任务

```python
def start_background_task(block):      # 生产者：注册任务 + 启动 worker 线程
    threading.Thread(target=worker, daemon=True).start()
    return bg_id

def collect_background_results():      # 消费者：收集已完成结果 → 通知
    ...
```

**模式：生产者-消费者 + 观察者**。

- **生产者**：`start_background_task` 把工具调用丢进工作线程
- **消费者**：`collect_background_results` 收集完成结果
- **观察者**：结果以 `<task_notification>` 注入 messages——LLM 是观察者，收到通知后决定下一步

**并发安全**：`background_lock` 保护共享字典——这是上一条学习记录（07）的核心场景。

**为什么需要**：慢操作（install/build/test）阻塞 agent_loop 太久。后台执行让 Agent 先干别的，完成后再通知。

### s14 — Cron 调度

```python
# 四层：Scheduler → Queue → Queue Processor → Consumer
cron_scheduler_loop: 每秒检查时间 → cron_queue.append(job)
queue_processor_loop: 队列非空 + agent 空闲 → 自动触发 agent_loop
agent_loop:           consume_cron_queue() → 注入 [Scheduled] 消息
```

**模式：生产者-消费者 + 调度器（Scheduler + Queue 解耦）**。

- **生产者**：cron_scheduler_loop（时间驱动）
- **缓冲**：cron_queue（线程安全队列）
- **消费者**：queue_processor_loop + agent_loop

**核心思想：调度与执行解耦**。调度器只看时间，不看 Agent 忙不忙；消费者只看队列，不看时间。中间隔着队列，谁先谁后无所谓。

**互斥设计**：`agent_lock` 保证用户输入和 cron 触发不会同时执行 agent_loop——用户优先级 > cron 优先级。

**从 s13 到 s14 的演进**：s13 是"人触发，后台执行"；s14 是"时间触发，自动执行"。Agent 从被动服务变为主动工作。

### s15 — Agent 团队（本阶段最复杂）

```python
# 事件驱动主循环
events = queue.Queue()
def input_reader(): ...   # 事件源 1：用户
def inbox_poller(): ...   # 事件源 2：队友/后台
while True:
    kind, payload = events.get()   # 谁来了处理谁
    agent_loop(history, context)

# 队友 = 独立线程 + 独立 messages[] + 独立邮箱
def spawn_teammate_thread(name, role, prompt):
    threading.Thread(target=run, daemon=True).start()

# 通信 = 文件邮箱（Actor 邮箱）
class MessageBus: send / read_inbox / peek
```

**s15 一次用了 4 个模式**：

| 模式 | 角色 |
|------|------|
| **Actor 模型** | 每个 Agent = 独立线程 + 独立状态 + 独立邮箱 |
| **生产者-消费者** | send_message 生产 → 邮箱缓冲 → read_inbox 消费 |
| **事件驱动** | 主循环 events.get() 统一分发所有触发源 |
| **中介者 + 黑板** | MessageBus 解耦通信；文件系统作为共享空间 |

**架构转折点**：s15 之前 Agent 只响应"用户输入"；s15 之后 Agent 响应**任何事件**（队友消息、后台完成、定时触发）。这是"从被动服务到主动协作"的范式跃迁，也是 s16-s20 多 Agent 平台的地基。

## 三、模式演进的脉络

把 15 章串起来看，有一条清晰的架构演进线：

```
【第一阶段：单 Agent 内核】
s01 循环（解释器） → s02 策略分发 → s03 责任链权限 → s04 观察者 Hook
  ↓ 循环稳定 + 扩展点就位，开始加"能力"

【第二阶段：规划与控制】
s05 规划-执行分离 → s06 函数调用（子 Agent）→ s07 懒加载（技能）
  ↓ 从"会执行"到"会规划、会拆解、会按需取知识"

【第三阶段：记忆与韧性】
s08 分级降级（压缩） → s09 快照+侧查询（记忆） → s10 模板+缓存（提示词） → s11 重试降级（容错）
  ↓ Agent 不再"一跑就废"，能压缩、能记忆、能自愈

【第四阶段：并发与调度】
s12 领域模型+仓储（任务） → s13 生产者-消费者（后台） → s14 调度器（定时）
  ↓ 从"单线程对话"到"多线程并行 + 时间驱动"

【第五阶段：多 Agent 平台】
s15 Actor + 事件驱动 + 中介者 + 黑板（团队）
  ↓ 从"一个 Agent 能干很多"到"一群 Agent 协作"
```

**每章添加的模式都是前一章能力的外延**，不是推翻重来。这印证了 CLAUDE.md 的核心设计原则：**循环不可变、层层叠加、独立可运行**。
