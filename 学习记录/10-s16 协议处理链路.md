# s16 协议处理链路完整走查：shutdown 与 plan approval 两条协议

> 本文把 s16（Team Protocols）的两条协议链路——**关机协议**（shutdown）和**计划审批协议**（plan approval）——从头到尾各走一遍，并用对比表讲清"两种协议，一套机制"到底复用在哪里。适合学完 s16 后复习，判断标准是：**你能不能用一张图画出一条协议消息从发出到状态闭合的完整链路**。

---

## 1. 协议机制全景：5 个零件散布在文件各处

协议不是某个函数，而是**跨函数、跨线程的协作模式**。它由 5 个零件组成：

| 零件 | 作用 | 位置 |
|---|---|---|
| `ProtocolState` + `pending_requests` | 状态存储（pending → approved/rejected） | `demo_code.py:612`（模块级） |
| **发起端** | 发请求 + 注册 pending 状态 | 有两个：`run_request_shutdown`（Lead 侧，999 行）、`_teammate_submit_plan`（队友侧，959 行） |
| **响应端** | 收到请求 → 回响应 | `handle_inbox_message`（队友侧，767 行） |
| **匹配端** | 收响应 → 凭 request_id 关联 → 更新状态 | `match_response`（635 行） |
| **统一入口** | 保证协议路由不丢 | `consume_lead_inbox`（690 行） |

**核心思想**：request_id 关联 + 状态机追踪。**谁都能发起，谁都能响应**——发起方决定请求方向，但机制完全对称。

---

## 2. 协议的共同骨架

无论哪种协议，都走同一个四步模式：

```
① 发起端注册状态：pending_requests[req_id] = ProtocolState(status="pending")
② 发起端发请求：   BUS.send("xxx_request", {request_id})
③ 响应端处理：     handle_inbox_message → BUS.send("xxx_response", {request_id, approve})
④ 匹配端闭合：     consume_lead_inbox → match_response → status = approved/rejected
```

request_id 是贯穿全链路的**关联键**：请求带着它出去，响应带着它回来，`match_response` 凭它找到原始请求。相当于 HTTP 的 correlation ID。

### 3.3 shutdown 之后：线程是怎么"关闭"的？

先纠正一个直觉：**Python 线程没有 shutdown 方法，也杀不了。** `threading.Thread` 只有 `start()` / `join()` / `is_alive()` 这些方法，**没有任何 `stop()` / `terminate()` / `kill()`**。线程一旦启动，外部就无法强制终止它——Python 层面根本不提供这种能力（见下方"为什么没有 terminate"）。所以 shutdown 走的是**合作式退出（cooperative cancellation）**——线程自己决定结束，不是被外部掐死。

**关键：一个标志位 + while 循环条件**

真正的"关机开关"是 `run()` 里的局部变量 `shutdown_requested`：

```python
# demo_code.py:858
shutdown_requested = False
while not shutdown_requested:       # ← 循环条件就是"还没收到关机请求"
    ...
    if should_stop:
        shutdown_requested = True   # ← 收到 shutdown_request 后置 True
        break                       # ← 跳出当前轮
```

线程不会被"关闭"，而是**让 while 条件变 False，循环自然跑完**。

**完整流程：线程怎么"自然消失"**

```
① 收到 shutdown_request
   handle_inbox_message → return True
   → should_stop=True → shutdown_requested=True → break
   ↓
② while 条件 False，循环结束
   ↓
③ 执行收尾代码（demo_code.py:933）：
   - 提取最终摘要 summary
   - BUS.send(name, "lead", summary, "result")   # 把成果发回 Lead
   - active_teammates.pop(name, None)             # 从活跃登记表划掉
   - print("[teammate] {name} finished")
   ↓
④ run() 函数走到最后一行，return
   ↓
⑤ threading 框架看到线程函数返回 → 自动清理线程资源 → 线程真正结束
```

**run() 函数返回的那一刻，线程就结束了。** 没有任何地方调用 `thread.kill()`——因为线程的生命周期 = 线程函数的生命周期，函数跑完，线程就没了。

**为什么叫"优雅关闭"**：因为给了线程**做完收尾的机会**——先发最终摘要（工作成果不丢）、再从 `active_teammates` 移除注册（Lead 侧据此知道"Alice 不在了"），然后才结束。对比暴力终止——进程直接消失，收尾代码根本来不及跑。

**一个直觉类比**：把 `run()` 想成一个车间工人——

- 他按 `while` 循环干活（读单子 → 干活 → 汇报）
- `shutdown_requested` 是一面**红旗**
- 收到关机请求 = 有人举红旗 → 他看到红旗就停下手中的活（`break`）
- 然后**自己完成收尾**：关机器、写交接单、从打卡表划掉自己名字
- 最后自己下班（函数返回，线程结束）

没有监工来强行拖走他——所以也不会有"线程被杀死却留下烂摊子"的问题。

**补充：`daemon=True` 是什么？**

队友线程创建时是 `daemon=True`（`demo_code.py:954`）。它和"线程如何退出"**无关**，管的是**主进程退出时**的行为：如果主程序退出而队友线程还活着，daemon 线程**不阻塞进程退出**（进程直接结束，线程被丢弃）。这是防止"主程序关了你还在后台挂"的兜底，不是关机协议的一部分。

**为什么 Python 没有 `Thread.terminate()`？——不是 GIL 的锅**

很多人直觉归咎于 GIL，但**方向对了一半，根本原因不是 GIL**。

**用反证法先排除 GIL**：Java 没有 GIL（它靠 JVM 内存模型管理并发），但 Java 的 `Thread.stop()` 同样被标记为 **deprecated（废弃）**。如果"没有 terminate"是 GIL 导致的，没有 GIL 的 Java 应该可以放心杀线程——但它也不能。所以根本原因在别处。

**真正的原因：共享内存 + 共享锁状态。** 进程内的所有线程共享同一份地址空间（同一内存、同一批锁对象、同一堆文件句柄），强杀一个线程会带来三个连环灾难：

```
① 它改了一半的数据永远停留在半更新状态
   self.tasks.append(item)   # 线程 A 在这句被杀
   self.counter += 1         # ← 这句没执行
   → tasks 多了但 counter 没加，其他线程读到前后矛盾的数据

② 它持有的锁永远不会释放
   锁不是线程私有属性，而是进程内存里的一个对象——
   线程 A 拿到锁后被杀，锁对象还在，状态是"已获取"，
   但获取它的线程没了，没人能把它放回"未获取"状态
   → 所有等这把锁的线程全部死锁

③ with / finally 的清理代码不执行
   with open(f, "w") as fh: fh.write(...)   # 中途被杀
   → __exit__ 不执行 → 文件句柄、数据库连接、临时文件全部泄漏
```

**那 GIL 到底干了什么？** GIL 保证同一时刻只有一个线程执行 Python 字节码：
- ✅ 让单个字节码操作（如 `dict.get`）在解释器层面原子，dict/list 底层不用各自加锁
- ❌ **它不能让你安全杀线程**——跨多条字节码的复合操作照样有竞态，用户态的 `Lock` 是独立同步原语，解释器不知道也不负责替它释放

所以 GIL 不仅不是"可以放心杀线程"的理由，恰恰是它只保护了最浅的一层，深层一致性完全靠线程"自觉"协作。

**对比：进程为什么可以 `terminate()`** —— `multiprocessing.Process` 有 `terminate()` 且安全得多：
- 每个进程有**独立的地址空间**和独立的锁状态
- 强杀进程时，操作系统**整体回收**该进程的一切资源（内存、锁、文件句柄），不存在"锁留在别的进程里"的问题

所以"能不能强杀"的判据不是"有没有 GIL"，而是**"被杀者是否和杀它的人共享状态"**：线程共享一切 → 不能强杀，只能合作式退出；进程相互独立 → 可以强杀，OS 兜底回收。

**小结**：Python 线程没有 terminate，根本原因是线程共享进程的内存和锁——强杀会让共享状态半更新、让锁永久死锁、让清理代码不执行。这和语言无关（Java 同样禁止）。这也是多线程世界"让线程停下来"的标准做法永远是**合作式标志位**的原因——s16 的 `shutdown_requested` 正是让线程自己走到安全点再退出，而不是从外部掐断它。

**一句话总结**：s16 没有"关线程"，只有"告诉线程该停了自己会停"。`shutdown_requested` 标志位 + `while not shutdown_requested` 循环条件 + 函数自然返回，三件事合起来构成"优雅关闭"。这是 Python 多线程的标配模式——凡是看到"需要让线程停下来"的需求，答案都是合作式标志位。

## 5. 两条链路对比：到底复用了什么

| 对比项 | shutdown | plan approval |
|---|---|---|
| **发起方** | Lead | 队友 |
| **响应方** | 队友 | Lead |
| **发起工具/函数** | `request_shutdown`（999 行） | `submit_plan` → `_teammate_submit_plan`（959 行） |
| **响应函数** | `handle_inbox_message`（767 行） | `review_plan`（1039 行） |
| request 消息 | `shutdown_request` | `plan_approval_request` |
| response 消息 | `shutdown_response` | `plan_approval_response` |
| 状态机 | pending → approved/rejected | 同 |
| **request_id 关联** | ✅ | ✅ |
| **match_response 闭合** | ✅（consume 时） | ✅（consume 时） |
| **响应后队友是否退出** | ✅ 是（return True） | ❌ 否（return False） |
| 响应后队友下一步 | 发摘要 → 线程结束 | 注入审批结果 → 继续干活 |

**"一套机制"体现在 5 个复用点**：

1. **`request_id` 贯穿**——两条链路都靠它关联请求与响应，无需额外匹配逻辑
2. **`ProtocolState` + `pending_requests`**——状态存储完全复用，只是 `type` 不同
3. **`match_response`**——同一条函数处理两种响应，靠"类型必须匹配"校验区分
4. **`consume_lead_inbox` 统一入口**——两条链路的响应都从这儿进
5. **`handle_inbox_message` 分发器**——新增协议只需加一个 `if` 分支

**本质差异只有一个**：响应后队友是否退出（shutdown 要结束线程，plan 要返回工作循环）。这就是 `handle_inbox_message` 返回 `True`/`False` 的全部意义——**返回值语义 = "这个协议消息是否需要我退出"**。

## 6. 关键机制拆解（复习必看）

### 6.1 队友侧的双入口读收件箱

```
外层 while（忙时）      idle loop（闲时）
    │                        │
    ├─ LLM 轮次前读一次      ├─ 每秒 sleep(1) 轮询
    │                        │
    └─ 都是：read_inbox → 分类 → 协议消息走 handle_inbox_message
```

**为什么需要两处**：队友干活时（外层），Lead 消息能被 LLM 轮次前读到；队友空闲时（idle loop），每秒轮询保证能收到 shutdown_request。缺一处，就有收不到关机请求的死角。

### 6.2 `match_response` 的三道理防线

```python
state = pending_requests.get(request_id)   # ① request_id 必须存在（防伪造/过期）
if state.type == "shutdown" and response_type != "shutdown_response":
    return                                  # ② 类型必须匹配（shutdown 不能批准 plan）
if state.status != "pending":
    return                                  # ③ 幂等（已处理的不重复处理）
state.status = "approved" if approve else "rejected"
```

### 6.3 `consume_lead_inbox` 为什么必须统一入口（s16 修复的 bug）

s15 中 `check_inbox` 工具和主循环**各自直接读收件箱**——如果 `check_inbox` 先读走了协议响应消息，主循环就看不到它们，`match_response` 不被调用 → 协议请求**永远 pending**（Lead 干等队友的响应）。

s16 让两个调用方（`check_inbox` 工具 + 主循环）都走 `consume_lead_inbox`，先路由协议再返回消息，保证协议状态不丢。

### 6.4 状态机：单向流转

```
pending ──收到响应──→ approved / rejected
```

注册时 `status="pending"`，由 `match_response`（Lead 收到响应时）或 `run_review_plan`（Lead 审批时）更新。**没有从 approved/rejected 回退 pending 的路径**。
