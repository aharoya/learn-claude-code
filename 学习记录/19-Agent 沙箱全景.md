# Agent 沙箱全景：从概念到进程沙箱、容器、虚拟机，再到业界主流选择

> 本文用"由内而外、由抽象到具体"的脉络，把 Agent 的沙箱彻底讲清楚：**先搞懂沙箱是什么（一个目标，不是一种机制），再看实现它的四种方式（进程沙箱/容器/虚拟机/云沙箱），然后落到业界主流的路线选择，最后用 Claude Code 官方文档的"六种沙箱环境"做最终核对**。读完你会有一套清晰的"墙有多厚"的坐标系，不再把沙箱和容器混为一谈。

---

## 1. 先搞懂：沙箱是"目标"，不是"机制"

**沙箱 = 一个概念/目标**：让程序在受限环境里运行，它碰不到不该碰的东西。

实现这个目标的**方式（机制）有很多种**：

```
目标：沙箱（让程序受限运行）
  ├── 方式A：进程沙箱 —— 没换位置，本机加 OS 限制（Claude Code 默认）
  ├── 方式B：容器（Docker）—— 换个隔离环境跑
  ├── 方式C：虚拟机 —— 换个独立 OS 跑（最强）
  └── 方式D：云沙箱 / microVM —— 云端一次性隔离环境
```

> ⚠️ 关键纠正：**沙箱 ≠ 容器**。沙箱是"受限运行"这个目标，容器、进程沙箱、虚拟机都是实现它的不同方式。就像"安全"不是一种锁，而是"上锁/保险箱/保安"共同达到的状态。

### 类比钉死

| 概念 | 类比 |
|------|------|
| **沙箱（目标）** | "安全"——让东西不被偷 |
| 进程沙箱（方式A） | 房间门上锁（东西还在房间，但拿不出来） |
| 容器（方式B） | 放进保险箱（东西换了个受保护的容器） |
| 虚拟机（方式C） | 放进另一栋有独立保安的楼（彻底分离） |

---

## 2. 四种实现方式对比（核心表）

| # | 方式 | 命令跑在哪 | 隔离靠什么 | 技术实现 | 代表工具 |
|---|------|-----------|-----------|---------|---------|
| A | **进程沙箱** | 你本机（没换地方） | OS 拦截越界行为 | macOS **Seatbelt** / Linux **bubblewrap+seccomp** / Windows 需 WSL2 | **Claude Code 默认** |
| B | **容器（Docker）** | 容器里（换环境） | 容器自带隔离（FS/进程/网络） | Docker / Podman，镜像 + 容器运行时 | **OpenHands、Cline 容器模式** |
| C | **虚拟机** | 独立 OS 里（彻底分离） | 独立内核，最强 | QEMU / VirtualBox / Firecracker | 评估不可信代码 |
| D | **云沙箱** | 云端一次性沙箱 | microVM 级隔离 | Firecracker 等，托管 | **OpenAI Codex、E2B** |

**核心区别一句话**：进程沙箱**没换位置**（还是本机，只是加限制）；容器/虚拟机/云沙箱**换了位置**（换到隔离环境里）。

## 3. 进程沙箱深入：它是怎么限制 bash 的

### 为什么叫"进程"沙箱

因为 bash 命令是**活的东西**——它不是读一个文件就结束，而是一个**进程**（正在运行的程序），它还能再启动子进程（脚本里再跑脚本、`npm` 再调 `node`）。

所以限制 bash 不能只限制"文件路径"，得限制**这个进程整个运行过程中能做什么**。进程沙箱以进程为单位套规则，连同它产生的所有子进程一起罩住：

```
bash 命令 = 一个进程（活的）
  └─ 它 spawn 的子进程（脚本、node、kubectl...）全在这个笼子里
```

### 怎么限制的：三条规矩由 OS 强制执行

| 限制 | 怎么实现 | 例子 |
|------|---------|------|
| **文件系统限制** | 拦截"打开/写入文件"的系统调用，只允许指定路径 | 只让写当前目录；读 `~/.ssh` → 拦 |
| **网络限制** | 把命令的网络流量强制改道走代理，按域名过滤 | `curl http://任意网址` → 拦；只允许 api.github.com |
| **进程限制（可选）** | 用 seccomp 过滤"创建进程/访问内核"的系统调用 | 阻止命令读取密钥、提权 |

### 生活类比

命令是一个"工人"，进程沙箱不是给他换工作地点（还是在你家），而是：

```
给他规定三条硬规矩，违反就立刻喊停：
  ① 只能动这个工具箱（文件系统）
  ② 只能打这几个电话（网络）
  ③ 不许撬锁（进程/内核）
```

工人还是在你家干活，只是**每次伸手碰不该碰的东西，都有一只手（OS）按住他**。

### 为什么限制的是 bash，而不是读写文件工具

回到 Claude Code 的一个关键设计：**内置的 Read/Write 文件工具不被沙箱罩**（它们有自己的路径校验），而 **bash 被沙箱罩**。

原因：bash 太强了——它能 `rm -rf`、能读任意文件、能联网、能启动任何程序。而 Read/Write 工具是 Claude Code 自己写的、可控的（只接受 path 参数、有安全检查）。

```
Read/Write 工具 = 自带门禁（Claude Code 自己管的）
bash          = 万能钥匙，太危险 → 必须用 OS 级进程沙箱罩住
```

## 4. 业界主流路线选择

### 五条路线全景（按墙的厚度从薄到厚）

| # | 路线 | 命令在哪 | 隔离靠什么 | 代表工具 |
|---|------|---------|-----------|---------|
| 1 | **本机直执行** | 本地 | 无隔离，靠权限门兜底 | 早期 AutoGPT、Cline 本地模式 |
| 2 | **本机进程沙箱** | 本地 | 内核机制拦越界（Seatbelt / bubblewrap+seccomp） | **Claude Code 默认、Cursor** |
| 3 | **远程主机（SSH）** | 远程一台已有机器 | 取决于那台机器（可能无隔离） | LangChain SSH 工具、连 CI/服务器 |
| 4 | **Docker 容器** | 本地/远程的容器 | 容器自带隔离（FS/进程/网络） | **OpenHands、Cline 容器模式、E2B** |
| 5 | **云沙箱 / microVM** | 云端一次性沙箱 | Firecracker 级虚拟机隔离 | **OpenAI Codex、E2B 云端**、GitHub Codespaces |

### 业界三派

| 派别 | 路线 | 理念 | 代表 |
|------|------|------|------|
| **本地 + 权限派** | 1 → 2 | 体验第一，最小隔离 + 权限兜底 | Claude Code、Cursor |
| **容器派** | 4 | 安全 + 干净可复现 | OpenHands、Cline |
| **云沙箱派** | 5 | 最强隔离、托管 | OpenAI Codex、E2B |

### 什么时候选哪条

```
墙从薄到厚：
  本机直跑（没墙）→ 本机沙箱（一堵软墙）→ SSH 远程（墙取决于那台机）
  → Docker（玻璃房）→ microVM（碉堡）
```

| 你的目标 | 选哪条 |
|---------|--------|
| 改自己代码（快速、方便） | 路线 1/2（Claude Code 默认） |
| 跑别人/不可信的代码 | 路线 4/5（容器/云沙箱） |
| 要贴近生产环境调试 | 路线 3（SSH 远程） |
| 防恶意项目、最强隔离 | 路线 5 / 虚拟机 |

**选路线 = 回答一个问题：你让 Agent 碰的东西，值不值得给"手"配一堵墙，墙要多厚。**

## 5. Claude Code 官方：六种沙箱环境（官方文档原文核对）

Claude Code 官方文档（[选择沙箱环境](https://code.claude.com/docs/zh-CN/sandbox-environments)）明确列出 **6 种沙箱方法**。注意：**前两种在主机操作系统上运行（不用容器），其余四种把 Claude Code 放进容器或虚拟机内**——这正好印证了我们第 2 节的"进程沙箱没换位置、容器/VM 换了位置"。

| # | 方法 | 隔离内容 | 需 Docker | 设置量 |
|---|------|---------|----------|--------|
| 1 | **Sandboxed Bash tool**（内置） | 仅 Bash 命令及子进程 | 否 | macOS 最少；Linux/WSL2 较少 |
| 2 | **Sandbox runtime**（`@anthropic-ai/sandbox-runtime`） | **整个 Claude Code 进程**（含文件工具、MCP 服务器、hooks） | 否 | 较少 |
| 3 | **Dev container** | 完整开发环境 | 是 | 中等 |
| 4 | **Custom container** | 完整开发环境 | 是 | 中等到高 |
| 5 | **Virtual machine** | 完整操作系统 | 否 | 高 |
| 6 | **Claude Code on the web** | 完整 OS，Anthropic 托管 | 否 | 无（需订阅 + GitHub） |

### 5.1 方法 1 vs 方法 2：进程沙箱的两个粒度（最重要的区分）

官方原文强调：**内置文件工具、MCP 服务器、hooks 默认直接在主机上运行，只有 Bash 被方法 1 罩住**。要把它们全部包进隔离边界，需要方法 2/3/4。

```
① Sandboxed Bash tool → 只罩"手"（bash 命令），文件工具/MCP/hooks 仍在宿主上
② Sandbox runtime    → 罩住"整个人"（整个 Claude Code 进程，含文件工具/MCP/hooks）
```

方法 2 用**同一套** Seatbelt/bubblewrap 隔离，但把边界从"bash 命令"扩大到"整个进程"。默认拒绝所有写入和网络访问，需在 `~/.srt-settings.json` 配置，用 `npx @anthropic-ai/sandbox-runtime claude` 启动。**beta 研究预览版，配置格式可能变动**。

### 5.2 官方反复强调的三个要点

**① 隔离 ≠ 数据隐私**
> "隔离不会改变发送给模型的内容。您的提示和 Claude 读取的文件无论是否使用沙箱，都会传输到 Anthropic API。"

→ 沙箱只挡"命令能碰什么"，**不挡"什么数据发给模型"**。这是容易误解的点。

**② 分层思想：沙箱可以叠加**
> "您可以分层方法：在容器或虚拟机内运行沙箱化 Bash 工具可在外部环境边界之上为您提供操作系统级命令限制。"

→ 进程沙箱和容器**不是二选一**，可叠加：容器外边界 + 内部 bash 沙箱，两层防护。

**③ 无人值守必须用强的隔离**
> "始终在容器、虚拟机或 sandbox runtime 内运行 `--dangerously-skip-permissions` 会话。"

→ 关掉权限提示后，沙箱边界就是唯一防线，所以必须用能罩住整个进程的（2/3/4/5/6），**不能只用方法 1**（它只罩 bash，文件工具/MCP/hooks 无保护）。

### 5.3 官方选型对照（目标 → 方法）

| 你的目标 | 官方建议 |
|---------|---------|
| 自己机器上减少权限提示 | ① `/sandbox` 启用 |
| 无人值守跑 `--dangerously-skip-permissions` | 预配置 dev container、任意容器/VM、或 ② sandbox runtime |
| 隔离 MCP/hooks 且不用 Docker | ② sandbox runtime |
| 处理**不受信任的存储库** | ⑤ VM 或 ⑥ Web 版 |
| 团队标准化沙箱 | ③ dev container（复制进仓库） |
| 零本地设置的设备 | ⑥ Web 版 |
| 本机 Windows（无 WSL2） | 容器/VM，或 WSL2 内跑 Bash 沙箱 |

### 5.4 与业界路线的最终对应

| 我们的五路线（第 4 节） | Claude Code 六档 |
|------------------------|------------------|
| ② 本机进程沙箱 | ① Sandboxed Bash tool |
| （进程沙箱全量版） | ② Sandbox runtime |
| ④ Docker 容器 | ③ Dev container + ④ Custom container |
| （虚拟机） | ⑤ Virtual machine |
| ⑤ 云沙箱 / microVM | ⑥ Claude Code on the web |

唯一没对齐的是我们的路线③ **SSH 远程**——Claude Code 的沙箱体系里没有 SSH 这条，它聚焦在"本机隔离"上。

### 5.5 Sandbox runtime vs Docker 容器：范围相同，位置不同

**容易混淆**：两者隔离范围都写着"整个 Claude Code 进程"，看起来一样。但"罩住整个进程"有两种完全不同的做法：

```
做法一（Sandbox runtime）：进程还在宿主机上跑，OS 用规则限制它（没换位置）
做法二（Docker）：          进程搬进独立容器里跑，和宿主机隔开（换了位置）
```

| 维度 | Sandbox runtime | Docker 容器 |
|------|----------------|------------|
| **Claude Code 跑在哪** | **宿主机**（没换位置） | **容器里**（换了位置） |
| **隔离机制** | 进程沙箱：Seatbelt / bubblewrap（OS 给进程套规则） | 容器：namespaces + cgroups（独立文件系统/进程表/网络栈） |
| **文件系统视角** | 还是宿主机 FS，只是限制能写/读哪些 | 容器自己的 FS，默认和宿主隔离（除非挂 volume） |
| **网络视角** | 流量走宿主机上的 SOCKS5 代理 | 容器独立网络命名空间 |
| **依赖 Docker** | **否** | 是 |
| **隔离强度** | 中（共享内核，进程理论上可尝试逃逸） | 更强（独立环境，进程表/网络栈都隔离） |
| **启动方式** | `npx @anthropic-ai/sandbox-runtime claude` | `docker run ... claude` |

**一句话：Sandbox runtime 是在宿主机上给进程"套规则"（本机加锁）；Docker 是把进程"搬进隔离环境"（搬家）。**

**为什么官方把两者都列出**——适用场景不同：

- **不想装 Docker、又想把整个 Claude Code（含 MCP/hooks）包住** → Sandbox runtime（轻，但隔离靠宿主 OS）
- **要更强的隔离、或已在用容器化基础设施** → Docker（重，但隔离更彻底）

**且两者可以叠加**——在容器里再开 Sandbox runtime，就是"外部容器边界 + 内部进程沙箱"两层防护（官方文档提到"在容器内分层内置 Bash 沙箱"）。

## 一句话总结

> **沙箱是"让程序受限运行"的目标，不是一种机制**——进程沙箱（本机加锁）、容器（换环境）、虚拟机（换 OS）、云沙箱（云端 microVM）都是实现它的方式。Claude Code 默认用"进程沙箱"（命令还是在本机跑，只是被 OS 用文件/网络/进程三条规则罩住），容器是"换地方跑"的更强隔离。业界路线从"本机直跑"到"云沙箱"墙越来越厚，选哪条取决于你让 Agent 碰的东西值不值得配墙、墙要多厚。
